# Performance observations

Recorded 2026-10-30T16:04:44.948Z, actual Node v26.12.1 and Chromium 156.0.8078.4. These are local Windows observations of private synthetic fixtures and actual production Nitro/static builds. They are descriptive measurements, not a causal before/after speedup claim. The user operating system page cache and unrelated host activity were uncontrolled.

The inspectable [per-repetition data](data/performance-observations.json) contains all observations used below. Each comparable timed condition has five repetitions. Median uses the middle sorted value, nearest-rank p95 is the largest of five values (a small sample, not a population tail estimate).

## Production HTTP paths

Each fixture starts with a fresh viewer cache unless its condition explicitly says warm/restarted. The production Nuxt routes use the real LiveViewerRuntime, reconciler, materializer and source store. The metadata case includes 3,000 metadata paths and a 64 MiB unopened source, browses typed groups and active/archive scope, then waits 1,200 ms across the actual 1,000 ms reconciliation interval. Every repetition observed zero rollout filesystem operations, body bytes, decode work, normalized sessions, rollout watchers and source writes. The plain selected positive control observes actual rollout bytes, so the zero is not produced by a disabled source reader.

Metadata first-response median/p95 was 947.75/1988.94 ms. The complete fixture-creation → reset → first response → sequential group/title browsing → quiet observation median/p95 was 3585.81/5481.59 ms. First response and browsing run in the unchanged 5 s test body, only the fixed quiet interval and final assertions run in that same case's owned cleanup hook (also with its unchanged limit), before closing its exact runtime. These separate lifecycle limits are not an aggregate 5 s responsiveness SLA. Abort signals and server owner/generation fencing prevent late cases from observing or replacing a later runtime. A real deferred source-directory enumeration is rejected by the identical quiet guard.

The metadata table duration includes runtime reset plus the first response, whereas the request-only first-response statistic above starts after reset. The full-probe statistic additionally includes fixture construction, sequential browsing and the quiet interval.

Rollout bytes count the instrumented main-process fs/read-stream operations, requested lease bytes and decoder output are separate counters. They exclude SQLite engine I/O and background native worker copy/hash reads, so they are not total physical disk traffic. SQL counters count returned rows/payload bytes, not engine-scanned pages. Runtime memory is sampled every 10 ms and can miss a shorter peak, RSS includes workers while heap fields describe the main isolate. Memory peaks and event-loop delay reset per fixture, then accumulate across that fixture's cold/older/append or cold/warm sequence (they cannot be attributed solely to its last operation). HTTP-only conditions have no DOM.

HTTP fixture resets create fresh viewer caches and reset counters, they do not restart the emitted Node server process. Sampled memory can include loaded code, runtime state and allocations from preceding cases that garbage collection has not reclaimed. These samples are not isolated per-operation allocation or leak measurements.

The 32 MiB native-source condition first serves raw selected content while its background snapshot is preparing, then times the first native-backed page after the actual snapshot manifest is ready. No native SQL result was observed before readiness, the subsequent native item payload counter is positive. This condition is separate from the physical multi-GiB worker qualification below.

## Multi-GiB native snapshot and packaging

Each repetition creates a valid SQLite database with 65 fully allocated 32 MiB BLOB rows plus a small indexed native conversation. The harness checks the private source fixture with quick_check before starting the viewer. The actual background worker copies, validates and hashes a private snapshot, actual native item queries succeed afterward. The runtime operates with its cwd inside the private fixture, the emitted server entry imports the emitted Nitro chunk containing the inline eval worker, whose body uses Node builtins. Entry/chunk hashes are in the data, no repository TypeScript loader or CWD fallback is used.

## Generated and live browser paths

Both modes use actual emitted application code. Static observations run against the actual generated Nuxt output, saved payload reader, Pagefind and offline server. Live observations run the root production server from a private fixture cwd, with isolated viewer configuration/cache. Controlled favicon/OpenGraph acquisition is preseeded through the real services, then both live acquisition settings are disabled. Every observation uses a fresh Chromium context (browser HTTP cache cold), the live cold priming context is recorded separately and excluded from the five comparable warm-viewer measurements. Static files are already in the uncontrolled OS cache after generation/verification.

## Reproduction and limits

A separate five-pair in-memory SQLite diagnostic kept 3,000 rows, selected 20 rows and included duplicate/unmatched order IDs. The old correlated ordering query median/p95 was 191.31/193.02 ms, the materialized first-position relation measured 2.72/3.55 ms. Exact SQL, query plans and all five pairs are retained in the data. This establishes the narrower query behavior, not a causal whole-application speedup.

Additional diagnosis found repeated immutable Zod schema construction (375.75 ms inclusive in a single instrumented CPU profile, overlapping parent scopes are not additive) and per-row ownership statement preparation. Reusing validators preserves field diagnostics and flag transforms, batched ownership retains rollback and independent authority/freshness semantics. The original ownership .run component was about 85.49 ms across 6,000 writes, so it did not explain the whole first-response delay. Later observations had different polling/write counts and are not a matched end-to-end comparison. A bounded Info-script scan also reduced retained script text, but observed total duration/RSS increased from 1.949 s/1.961 GB to 2.567 s/2.293 GB, no total performance improvement is claimed from that change.

Run the standard source/release commands in README. The repeated HTTP matrix is tests/http/acceptanceMetrics.test.ts, use VIEWER_METRICS_OUTPUT to save its JSON. The physical scale probe is opt-in: set VIEWER_LARGE_NATIVE=1 and run pnpm exec vitest run --project http tests/http/nativeLarge.test.ts, it creates and removes private multi-GiB fixtures. The normal suite skips those five opt-in cases, they were run separately for this observation. Existing test, hook, coverage and geometry thresholds were preserved.

Intermediate failures were retained during implementation: sandbox source/path restrictions, an afterAll call after Nuxt teardown, assumptions about Nitro entry versus worker-chunk layout, a Windows cwd cleanup lock, concurrent-build 5 s test timeouts, and a real static-search all-hit hydration regression. Published observations use the successful receipts, not those failed runs. Independent implementation reviews remain deferred. HTTP production-build suites now run after the parallel pure/Nuxt projects and the existing Pagefind group, rather than increasing timeouts.

No whole live Codex-home immutability or universal supported-artifact claim is made. See [history and artifact contracts](history-and-artifact-contracts.md) for representation, coverage, oversized-record and retained-copy limits. The measured cold/warm conditions differ, their absolute numbers should not be treated as an apples-to-apples native-versus-compression speed comparison.
